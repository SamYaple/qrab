# VM operator

The namespaced Rust operator owns only VM Pods, their ConfigMaps, NIC anchor
Pods (it also deletes the relay CiliumNetworkPolicies of the removed stream
datapath), the VM's Redfish and migration CiliumNetworkPolicies, the CHAP Secrets of
storage-service provisioned disks, a live migration's target state PVC, and
the `qrab-guest-*` ClusterStaticEntries of `spec.guestIdentity`
(`src/guest_identity.rs`, bounded by `guest-identity.yaml`).
Other PVCs and console entrypoints stay explicit Kubernetes resources. Manual
and unproven TPM/firmware identity claims stay retained. The user-approved
dashboard deletion flow permits GC ownership only for the exact launch's
state claim: matching dashboard labels, VM annotation, namespace, referenced
claim name and valid launch IDs; never adopt a foreign or legacy claim based
on the dashboard label alone. After successful migration an operator-created
previous state PVC can also be removed (docs/migration.md). Keep one replica
with Recreate rollout strategy.

The CRDs and the dashboard update policy are generated by `cargo run -p
qrab-operator -- crd|migration-crd|dashboard-update-policy` into
`contrib/kubernetes/operator/{crd,migration-crd,dashboard-update-policy}.json`.
Edit the Rust API and regenerate; `contrib/check-runtime.sh` compares them.
No guest NIC, arbitrary Pod template, anonymous BMC or Kubernetes API token in a
VM pod: guest NICs are kernel taps in separate NIC anchor Pods, built by
qrab-netd (docs/networking.md). Keep image digests pinned, validate ownership before patch/delete, and
set immutable CR UID as manager state_id. See docs/operator.md and docs/spire-vm.md.

Run `contrib/check-runtime.sh` and the documented live CR lifecycle checks.
